# MBRJ Main Redirect Page

Static single-page redirect hub for the MBRJ product suite.

## Files

- `index.html` - public home page: hero, "As featured in" press strip, one photo card per shoot (linking straight to its subdomain), WhatsApp/call contact band; internal tools are linked from the footer only
- `images/` - the four 4:5 WebP card covers, cropped from each shoot site's share image
- `images/press/` - 240px round WebP badges for the press strip (WallMag, WedWar, Thane Vaibhav), reusable on the shoot sites
- `client-experiences.html` - grouped page for pre-wedding, wedding, maternity, and baby shoot
- `internal-tools.html` - grouped page for easy select, attendance app, and admin
- `deploy.sh` - validates the site, then deploys it to the Nginx box (`./deploy.sh`)
- `robots.txt` - crawler rules + sitemap pointer (internal tools stays crawlable so its `noindex` is seen)
- `sitemap.xml` - lists the two public pages
- `favicon.svg` - main favicon source
- `favicon-32.png` - browser tab favicon fallback
- `favicon-512.png` - larger favicon asset
- `sw.js` - the offline cache (see below)

## Run Locally

Because this is a static page, you can either:

1. Open `index.html` directly in a browser, or
2. Serve it with any static server (recommended for route testing behind Nginx).

Example:

```bash
cd /Users/rohansolse/Documents/mbrj-main
python3 -m http.server 8080
```

Then open `http://localhost:8080`.

## Manual Deployment

This site is deployed as plain static HTML under `/var/www/mbrj-main` on the server.

- Sync the project folder to the server home folder using `rsync`
- SSH into the server
- Sync the folder into `/var/www/mbrj-main` using `sudo rsync`
- Fix ownership with `sudo chown -R`
- Fix permissions for files and folders
- Verify with `ls -l /var/www/mbrj-main`

Generalized copy commands:

```bash
rsync -av --delete \
  --exclude '.git/' \
  --exclude 'README.md' \
  --exclude 'MANUAL_DEPLOYMENT.md' \
  /Users/rohansolse/Documents/mbrj-main/ \
  rohansolse@192.168.1.33:/home/rohansolse/mbrj-main/
```

```bash
ssh rohansolse@192.168.1.33
sudo rsync -av --delete /home/rohansolse/mbrj-main/ /var/www/mbrj-main/
sudo chown -R www-data:www-data /var/www/mbrj-main
sudo find /var/www/mbrj-main -type d -exec chmod 755 {} \;
sudo find /var/www/mbrj-main -type f -exec chmod 644 {} \;
```

Step-by-step deployment instructions are available in `MANUAL_DEPLOYMENT.md`.

## Offline cache (`sw.js`)

The production server is not up around the clock, so a repeat visitor arriving while it is
down would otherwise get a browser "site not reachable" page. `sw.js` keeps the three pages
and their images in the visitor's own browser and serves those instead. It only helps
someone who has loaded the site at least once before — a true first visit during downtime
still fails, and so does a crawler. A CDN in front of the origin is the fix for that case;
this is the client-side half.

It is hand-written rather than generated by a bundler, because this repo has no build step —
`deploy.sh` rsyncs the folder as-is, and its allowlist already passes `*.js`. Two
consequences:

- **The precache list in `sw.js` is maintained by hand.** Adding a page or an image means
  adding it to `PRECACHE` too, or it is only cached once a visitor has actually fetched it.
  The list is the same set of files `./deploy.sh --check` prints, minus `robots.txt`,
  `sitemap.xml` and `sw.js` itself.
- **Nothing is served cache-first for long.** None of the filenames carry a content hash, so
  pages go network-first and images stale-while-revalidate. That is what keeps a deploy from
  being pinned behind a cached copy, and it is why there is no cache version to remember to
  bump on every edit.

`robots.txt` and `sitemap.xml` are never answered from the cache: a stale sitemap served to
Googlebot out of a visitor's own cache is worse than a failed request, and neither is any
use offline.

Each page registers the worker from an inline script on `load`, guarded by
`"serviceWorker" in navigator` so that opening `index.html` straight off the filesystem does
not throw.

Nginx should not long-cache `sw.js` — if a stale worker script is pinned, deploys stop
reaching returning visitors. Serve it with `Cache-Control: no-cache`.
